# قرارداد API Bidrano

این قرارداد برای جایگزین‌کردن داده‌های نمونه و `localStorage` با API طراحی شده است. مسیرهای مشتری اکنون در Next.js پیاده‌سازی شده‌اند. مسیرهای سفارش، تولید و حافظه محتوا هنوز قرارداد آینده هستند.

ذخیره‌سازی مشتری در این مرحله فایل محلی `.bidrano-data/customers.json` است؛ برای یک فرایند سرور محلی استفاده می‌شود. احراز هویت و دیتابیس مناسب استقرار عمومی هنوز پیاده‌سازی نشده‌اند.

## اصول مشترک

- ریشه همه مسیرها: `/api/v1`
- درخواست و پاسخ با `application/json` و متن UTF-8 هستند.
- شناسه‌ها رشته‌اند. تاریخ‌ها به صورت ISO 8601 UTC فرستاده می‌شوند.
- مقدارهای مجاز نوع محتوا: `Carousel`، `Post`، `Story`، `Reel`.
- وضعیت سفارش: `in-progress`، `review`، `approved`، `revision`.
- مبدأ سفارش: `Manual`، `Today's Suggestion`، `Start from a Topic`.
- در موفقیت، پاسخ در `data` قرار می‌گیرد. فهرست‌ها صفحه‌بندی دارند.
- خطاها در همه مسیرها قالب یکسان دارند.

### پاسخ موفق

```json
{
  "data": {},
  "meta": {
    "requestId": "req_123",
    "nextCursor": null
  }
}
```

`meta` اختیاری است؛ `nextCursor` فقط برای فهرست‌های صفحه‌بندی‌شده برگردانده می‌شود.

### پاسخ خطا

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "fields": { "topic": "Required" },
    "requestId": "req_123"
  }
}
```

`fields` اختیاری است. کدهای عمومی: `VALIDATION_ERROR`، `NOT_FOUND`، `CONFLICT`، `UNAUTHENTICATED`، `FORBIDDEN`، `RATE_LIMITED`، `INTERNAL_ERROR`.

## مشتری‌ها

### فهرست مشتری‌ها

`GET /api/v1/customers?limit=20&cursor=<cursor>`

پاسخ `data` آرایه‌ای از مشتری‌ها است. هر مورد دست‌کم `id`، `name`، `field`، `status`، `initials`، `audience` و `tone` را دارد؛ اطلاعات تماس، نشانی، موقعیت و قواعد برند اختیاری‌اند.

### دریافت یک مشتری

`GET /api/v1/customers/{customerId}`

مشتری کامل را در `data` برمی‌گرداند.

### ساخت مشتری

`POST /api/v1/customers`

درخواست، فیلدهای فرم مشتری را می‌گیرد: `name`، `field`، `audience`، `tone`، `phone`، `address`، `website`، `instagram` و `rules`. شناسه، وضعیت اولیه و حروف اختصاری را سرور تعیین می‌کند. پاسخ `201` و مشتری ساخته‌شده است.

فرم ثبت مشتری یک `Idempotency-Key` با قالب UUID می‌فرستد و در تلاش دوباره با همان داده، همان کلید را نگه می‌دارد. سرور برای کلید و داده یکسان همان مشتری را برمی‌گرداند؛ استفاده از همان کلید با داده متفاوت، خطای `409 CONFLICT` دارد.

### ویرایش مشتری

`PATCH /api/v1/customers/{customerId}`

فقط فیلدهای قابل ویرایش ارسال می‌شوند؛ پاسخ، مشتری کامل به‌روز‌شده است.

### انتقال داده‌های نسخه قبلی

`POST /api/v1/customers/import`

این مسیر مخصوص انتقال نسخه آزمایشی محلی است. ورودی `{ customers, profile? }` دارد؛ `customers` مشتری‌های ذخیره‌شده قبلی با شناسه `customer-<timestamp>` و `profile` فرم مشتری دندانپزشکی با نام‌های `name` و `field` است. تا ۲۰۰ مشتری در یک درخواست پذیرفته می‌شود. رکوردهای موجود سرور بازنویسی نمی‌شوند؛ پروفایل دندانپزشکی فقط هنگامی منتقل می‌شود که سرور هنوز داده اولیه دست‌نخورده دارد. پاسخ `{ data: { imported: number } }` است.

سقف بدنه JSON برابر ۱۲۸ کیبی‌بایت است و هنگام خواندن جریان درخواست کنترل می‌شود. کلاینت انتقال‌های بزرگ را بر اساس حجم و تعداد به چند درخواست تقسیم می‌کند. رکورد نامعتبر انتقال داده نمی‌شود و اصل داده مرورگر باقی می‌ماند. فقط فیلدهای شناخته‌شده فرم منتقل می‌شوند.

درخواست تغییردهنده با Origin خارجی با `403`، نوع محتوا غیر از `application/json` با `415 UNSUPPORTED_MEDIA_TYPE` و بدنه بزرگ با `413 PAYLOAD_TOO_LARGE` رد می‌شود. این کنترل‌ها جایگزین احراز هویت نیستند.

برای مشتری‌ها، `name` و `field` متن غیرخالی هستند. فیلدهای فرم باید رشته باشند؛ سقف `rules` ده‌هزار و سایر فیلدها دوهزار کاراکتر است. فیلد ناشناخته رد می‌شود. پارامتر `limit` بین ۱ و ۱۰۰ است و `cursor` شناسه آخرین مشتری صفحه قبلی است. درخواست خواندن حداکثر سه بار با فاصله ۵۰۰ و ۱۰۰۰ میلی‌ثانیه برای خطای شبکه یا ۵xx تلاش می‌شود؛ زمان انتظار هر تلاش ۱۵ ثانیه است. درخواست ثبت یا ویرایش خودکار تکرار نمی‌شود.

## سفارش و تولید

### ساخت سفارش

`POST /api/v1/orders`

```json
{
  "customerId": "dental-demo",
  "contentType": "Carousel",
  "topic": "موضوع محتوا",
  "instructions": "راهنمای تکمیلی",
  "source": "Manual"
}
```

`customerId`، `contentType` و `topic` الزامی‌اند؛ `instructions` و `source` اختیاری‌اند. سرور سفارش را با وضعیت `in-progress` ایجاد می‌کند و پاسخ `202` شامل سفارش کامل است. برای جلوگیری از ثبت تکراری هنگام قطع ارتباط، کلاینت در هر تلاش منطقی یک `Idempotency-Key` یکتا می‌فرستد؛ تکرار همان کلید باید همان نتیجه را برگرداند.

### فهرست سفارش‌ها

`GET /api/v1/orders?status=<status>&limit=20&cursor=<cursor>`

`status` اختیاری است و در صورت ارسال فقط سفارش‌های همان وضعیت برگردانده می‌شوند. پاسخ فهرست صفحه‌بندی‌شده از مدل کامل سفارش‌هاست. این مسیر برای صفحه تولید و فیلتر وضعیت استفاده می‌شود.

### دریافت سفارش و پیشرفت

`GET /api/v1/orders/{orderId}`

پاسخ شامل مدل سفارش فعلی است: `id`، `customerId`، `customerName`، `customerField`، `contentType`، `topic`، `instructions`، `source`، `status`، `createdAt`، `currentStep`، `pipeline` و در صورت بازبینی `revisionNote`.

`currentStep` عددی از صفر تا تعداد مراحل است. `pipeline` نام مرحله‌ها را به ترتیب اجرا نگه می‌دارد. هنگام تولید، کلاینت تا رسیدن وضعیت به `review` یا یک وضعیت نهایی، سفارش را هر ۲ ثانیه دوباره می‌خواند. پاسخ می‌تواند `Retry-After` را برای تنظیم فاصله بعدی تعیین کند.

### تصمیم بازبینی

`PUT /api/v1/orders/{orderId}/review`

تأیید:
```json
{ "decision": "approved" }
```

درخواست اصلاح:
```json
{ "decision": "revision", "revisionNote": "شرح تغییر لازم" }
```

فقط سفارش با وضعیت `review` قابل تصمیم‌گیری است. تأیید وضعیت را به `approved` می‌برد و درخواست اصلاح آن را به `revision` می‌برد. درخواست اصلاح بدون یادداشت با `400 VALIDATION_ERROR` رد می‌شود. تصمیم ناسازگار با وضعیت فعلی با `409 CONFLICT` رد می‌شود. پاسخ سفارش به‌روز‌شده است.

### ادامه سفارش پس از اصلاح

`POST /api/v1/orders/{orderId}/resume`

فقط سفارش با وضعیت `revision` قابل ادامه است. درخواست اختیاری می‌تواند `instructions` تازه داشته باشد. پاسخ سفارش را به `in-progress` برمی‌گرداند و مراحل تولید را برای نسخه تازه آغاز می‌کند. برای سفارش در وضعیت دیگر، پاسخ `409 CONFLICT` است.

## حافظه محتوا

### فهرست محتوای تأییدشده

`GET /api/v1/content-memory?customerId=<id>&limit=20&cursor=<cursor>`

`data` آرایه‌ای از `{ id, title, customer }` را برمی‌گرداند. فقط محتوای تأییدشده نمایش داده می‌شود؛ سرور باید هر مورد را بر اساس شناسه یکتا کند.

تأیید سفارش از مسیر تصمیم بازبینی، محتوا را به حافظه اضافه می‌کند. کلاینت برای ثبت جداگانه حافظه درخواست دیگری نمی‌فرستد.

## رفتار درخواست در رابط

- دکمه ارسال هنگام ثبت درخواست غیرفعال می‌شود و در انتظار پاسخ، حالت بارگذاری همان بخش دیده می‌شود.
- خطای اعتبارسنجی کنار فیلد مربوط نمایش داده می‌شود. خطای شبکه یا سرور پیام عمومی قابل فهم دارد و امکان تلاش دوباره می‌دهد.
- درخواست‌های خواندن قابل تکرارند؛ برای آن‌ها چند بار تلاش با فاصله افزایشی و سقف مشخص انجام می‌شود.
- درخواست‌های تغییردهنده خودکار تکرار نمی‌شوند، مگر با همان `Idempotency-Key`.
- هنگام رفتن کاربر از صفحه، درخواست خواندن لغو می‌شود. لغو درخواست نباید به عنوان خطای سرور گزارش شود.
- خطای `401` به مسیر ورود، `403` به پیام عدم دسترسی، `404` به صفحه یافت‌نشدن و `409` به تازه‌سازی داده و نمایش وضعیت فعلی منجر می‌شود.
- اگر polling تولید پس از ۲ دقیقه نتیجه نداد، polling متوقف می‌شود؛ سفارش حذف نمی‌شود و کاربر می‌تواند وضعیت را دوباره بررسی کند.
- جزئیات فنی و `requestId` در گزارش خطای داخلی نگه داشته شود؛ کلیدها و اطلاعات محرمانه در مرورگر ثبت نشوند.

## تصمیم‌های مانده برای شروع پیاده‌سازی بک‌اند

نسخه‌بندی همین قرارداد با `v1` شروع می‌شود. پیش از نوشتن API تولید، تیم باید روش احراز هویت و مالکیت مشتری‌ها، سیاست نگهداری و پاک‌سازی داده، و جزئیات ذخیره نسخه‌های قبلی محتوا پس از درخواست اصلاح را نهایی کند. هیچ کلید سرویس هوش مصنوعی نباید به مرورگر فرستاده شود.
